# AI 智能客服：完整流程梳理

> 本文基于当前代码实读整理（非设计稿），覆盖**入口 → 主链路 9 步 → 支撑模块 → 数据表 → 配置 → 关键设计决策**。
> 核心实现：`ruoyi-system` 模块 `AiServiceImpl.java`（约 1700 行，按职责分区）。
> 更新时间：2026-11-18。

---

## 一、整体架构一览

```
┌─────────────┐   POST /api/v1/chat/question      ┌──────────────────────────────┐
│  前端/网关   │ ────────────────────────────────→  │  AiController.handleQuestion │
└─────────────┘                                    └──────────────┬───────────────┘
                                                                  │
                              ┌───────────────────────────────────▼───────────────────────────────────┐
                              │            AiServiceImpl.handleUserQuestion（9 步主链路）              │
                              │  确定性分支优先 → 缓存 → 意图 → 向量检索 → 直达 → 大模型 → 后置校验     │
                              └───────┬───────────────┬───────────────┬───────────────┬───────────────┘
                                      │               │               │               │
                    ┌─────────────────▼──┐  ┌─────────▼──────┐  ┌─────▼────────┐  ┌──▼───────────────┐
                    │ MySQL(事实源)       │  │ Redis Stack    │  │ Elasticsearch │  │ 智谱大模型       │
                    │ 图书/订单/知识库/   │  │ 3 向量索引 +   │  │ 图书检索索引  │  │ glm-4-flash +    │
                    │ 对话/记忆/画像      │  │ 热门池/会话/缓存│  │ (只检索,不存据)│  │ embedding-3      │
                    └────────────────────┘  └────────────────┘  └──────────────┘  └──────────────────┘
```

**核心原则**：能用结构化数据确定性回答的，**绝不给大模型**（防幻觉、降延迟、省成本）；大模型是最后兜底，且输出要过后置校验。

**技术栈**：JDK 17 + Spring Boot 4.0.6 + Spring Cloud 2025.1.1 + Spring AI 2.0.2 + Nacos 3.2.3 + MySQL 8.0.46 + Redis Stack + Elasticsearch 9.2.2（官方 elasticsearch-java 客户端）+ 智谱 glm-4-flash / embedding-3（256 维）。

## 二、入口层：接口清单

### 2.1 对话主接口（`AiController`，前缀 `/api/v1/chat`）

| 方法 | 路径 | 说明 | 权限/身份约束 |
|---|---|---|---|
| POST | `/question` | **用户提问主入口**，支持多轮（`contextId`） | DTO `@Valid`；`userId` 由网关注入登录态为准，fail-closed |
| GET | `/profile/{userId}` | 画像快照（调试/联调）：画像表 + 记忆列表 + 实际注入 Prompt 的文本 | 必须登录；仅本人或管理员，否则 401/403 |
| GET | `/records` | 分页查对话记录 | `userId` 强制取登录态，禁止查他人 |
| GET | `/hot-questions` | 热门问题 TopN（Redis 热度 ZSet） | 公开 |
| DELETE | `/history/{contextId}` | 清空某会话的多轮历史（仅 Redis，不删 DB 记录） | 公开 |

**入参 `UserQuestionDTO`**：`userId`（`@NotNull`）、`question`、`contextId`（可选，空则自动生成 UUID）。
**响应 `AiResponseDTO`**：`answer`、`intent`、`recognizedIntent`（算法真实结果，不被分支覆盖）、`relatedKnowledges`、`contextId`、`responseTime`。

### 2.2 管理侧接口（均带 `@RequiresPermissions`）

| Controller | 前缀 | 主要能力 |
|---|---|---|
| `AiKnowledgeController` | `/api/v1/knowledge` | 知识库 CRUD（增改自动同步向量库） |
| `AiBookContentController` | `/api/v1/book-content` | 图书正文上传/大纲/在线浏览/原文件下载；上传需 `biz:book:edit` |
| `BookSearchController` | `/api/v1/book-search` | `/status` 查看 ES 状态；`/reindex` 手动全量重建（需 `biz:book:edit`） |
| `BizBookController` / `BizOrderController` | `/biz/book`、`/biz/order` | 图书/订单 CRUD（经网关加 `/system` 前缀转发） |

## 三、核心：主链路 9 步（`handleUserQuestion`）

> 判定顺序经过精心设计：**越"确定、实时、涉隐私"的分支越靠前**；越"贵、慢、不确定"的越靠后。
> 每个分支命中后统一做：写回答 → 落对话记录 → 追加会话历史 → 记耗时 → 返回。

### 前置：参数校验 + 身份绑定 + 限流 + 活跃打点

1. `questionDTO.validate()`：参数校验（未登录 `userId=null` 在此被 DTO `@NotNull` 拒绝）。
2. `resolveTrustedUserId(requested)`：**越权防护**——网关注入登录态 userId 时以登录态为准，不采信请求体自报值；仅无登录态的本地直连/内部调用才回退 DTO。
3. `checkRateLimit(userId)`：单用户每分钟上限（默认 20，Redis 故障 fail-open 不阻断问答）。
4. `memoryService.touchProfile(userId)`：原子 upsert 提问计数与最近活跃时间（所有分支都计入）。

### 步骤 1.1 订单号直达（`queryOrderStatus`）— 涉隐私，最优先

- 触发：问句中含订单号格式（`ORDER_NO_PATTERN`）。
- 行为：查 `biz_order` 真实状态，**归属校验**（必须登录且是本人订单，否则拒绝），收货人脱敏，返回订单号/状态/图书/数量/金额/下单时间。
- 不经向量检索、不经大模型，intent=`查询订单`。
- 无登录态一律不查（防匿名按订单号探测）。

### 步骤 1.15 发货/物流查询（`answerShippingQuery`）— 最新增强

- 触发：`SHIPPING_HINTS` = {发货、物流、快递、什么时候发、多久发}。
- **位置关键**：必须在库存查询之前——否则"红楼梦多久发货"里的裸书名会先命中库存、答成价格。
- 两级判定：
  1. **已登录 + 问句点名某书 + 本人名下有该书订单** → 直接返回真实订单状态（订单号 + `已发货/待发货` + 下单时间）。书名提取用 `findMentionedBookTitle()`（归一化 contains + 取最长匹配），订单查 `selectBizOrderList(userId, bookTitle)`，严格按登录 userId 过滤防泄露。
  2. 未登录 / 未点名书名 / 无本人订单 / 查询异常 → 回退知识库通用发货时效 FAQ（`selectByKeyword("发货")`，如"48 小时内发货"）。**该通用答案会写入热门池**（发货是最高频通用问题，不写会让热门列表缺一条）；分支 1 的订单状态含订单号/下单时间，属个人数据，**绝不入池**。
- intent=`知识库直达`。

### 步骤 1.2 图书在售查询（`answerStockQuery`）— 实时库存，不经大模型

- 触发：`isAvailabilityQuestion` = 命中 `STOCK_HINTS`（卖吗/多少钱/有货吗…）+ 疑问语气 + `AVAILABILITY_PATTERN`（有 X 书吗）+ 已知分类 + **裸书名精确匹配**（`matchedBareBookTitle`，支持《红楼梦》、重复输入"红楼梦红楼梦"，用 equals/整数倍而非 contains，避免"红楼梦读后感"误伤）。
- 检索词优先级：**书名号书名 > 裸书名命中值 > `extractTopic` 主题词**。
- 检索走 `searchBooks`（ES 优先、MySQL FULLTEXT/LIKE 降级），回答仅列真实在售图书的价格/库存。
- 为什么不经大模型：模型不知道实时库存，曾臆断"红楼梦不在我们的恐龙科普范围内"。
- intent=`图书在售查询`；命中后异步抽取记忆。

### 步骤 2 热门问题缓存（`chatStore.findHotAnswer`）

- key = 归一化问题（`AiTextUtils.normalizeQuestion`，"请问订单多久发货呢？"与"订单多久发货"收敛为同一条）。
- 命中直接返回知识库标准答案，跳过意图识别/向量检索/大模型；同时累加热度。
- **出口一致性**：缓存命中也落对话记录；但不再触发记忆抽取（首次回答时已抽过）。
- Redis 故障 → 返回 null 继续走正常链路（降级不报错）。

### 步骤 3 意图识别（`recognizeIntent`）

- 数据源：`ai_intent` 表（通过 `getAllIntentsCached` 走 Redis 5 分钟共享缓存）。
- 算法：按 `keywords`（逗号分隔）匹配问句，单字关键词跳过，按命中词长度加权（上限 6），取最高分意图；无命中=`未知意图`。
- 结果同时写入 `intent` 和 `recognizedIntent`（后者记录算法真实结果，避免被后续分支覆盖后无法判断识别成败）。

### 步骤 3.1 图书推荐（`isRecommendQuestion` + `recommendBooks`）

- 触发：意图=`图书推荐`，或兜底词表命中（`RECOMMEND_HINTS` 推荐/书单…，或 `TASTE_HINTS` 喜欢/预算… 与 `BOOK_WORDS` 同时出现，覆盖"我平时只看科幻，预算两百"这类无"推荐"二字的问法）。
- 行为：**走库存结构化检索**（真实价格/库存），不用 FAQ 语义召回；预算/偏好解析后过滤真实书单；Prompt 只允许用清单内数据。
- 后置：`guardHallucinatedTitles` 校验书名/价格真实性，不-real 则回退结构化书单，绝不编造。
- 推荐含用户偏好，**不写全局热门池**（隐私）。

### 步骤 4 向量检索（知识库独立索引）

- `SearchRequest`：query=问题，`topK=3`，`similarityThreshold=0.5`（智谱 embedding-3 256 维实测：中文相似问句余弦约 0.65，原 0.7 会全过滤掉）。
- 查 `aa_knowledge_index`（独立索引，全是知识库文档）；相似度从 `Document.score` 取。
- **消除 N+1**：向量文档 metadata 写入时已带 `knowledgeId/question/answer/category`，直接构造 `KnowledgeDTO`，不再逐条回查 MySQL。
- 最多保留 10 条；检索异常 → 空列表继续（旁路降级）。

### 步骤 5 知识库直达（`findDirectAnswer`）

- 判定优先级：**归一化文本匹配（准，主力） > 相似度阈值（安全阀，0.92）**。
- 0.92 的依据：实测相关/不相关问法分数都在 0.80 附近，0.80 会误判，抬高到 0.92 让该分支几乎不参与，主力靠文本匹配。
- 命中直接返回标准答案，跳过大模型（FAQ 从 ~15s 压到 ~1s）；同时**写入热门池**（只有标准答案可进，见隐私约束）。

### 步骤 6 大模型生成（最后兜底）

- 组装参考资料：知识库问答对 + 书籍正文片段（`bookContentService.searchBookChunks(question,3)`，命中则注明书名/章节）。
- 注入上下文：`memoryService.buildUserContext`（画像摘要/标签 + 最近 5 条记忆 + 语义召回 3 条，带 userId 过滤）+ `loadChatHistory(contextId)`（最近 6 轮）。
- **Prompt 分层**：规则放 `system` 角色（高指令层级，抗注入），用户数据放 `user` 角色并用 XML 标签包裹（`escapeXml` 防注入）；明确禁止编造书名/价格、禁止把画像当经营范围、禁止复述隐私。
- 调用 `chatClient.prompt().system(...).user(...).call().content()`。
- 输出过 `guardHallucinatedTitles` 后置校验：发现库里不存在的《书名》+价格 → 改走结构化推荐，绝不让编造内容落到用户面前。
- **不写全局热门池**（回答注入了画像，写全局池会泄露隐私）。

### 步骤 7 事务落库 + 异步记忆

- 编程式事务：`saveChatRecordAndUpdateKnowledge`（写 `ai_chat_record` + 更新知识库命中次数）。
- 异步（`@Async` 有界线程池 `aiMemoryExecutor`）：`extractAndSaveAsync` 抽取结构化记忆 → 写 `ai_user_memory` + `aa_memory_index` + 刷新 `ai_user_profile`。

### 步骤 8 隐私边界（热门池准入）

- 全局热门池不分用户，只收**通用型**问答：长度 4-60、不含 `PERSONAL_MARKERS`（我/孩子/预算/推荐/喜欢…）。
- 大模型回答因注入画像，**一律不进**热门池。

### 步骤 9 收尾

- 计算 `responseTime`；异常兜底：主链路已产出答案时不被旁路异常覆盖，仅在无答案时写"服务异常"文案；`ServiceException` 原样抛给全局处理器（不塞进 answer）。

## 四、支撑模块

### 4.1 三套独立向量索引（Redis Stack / RediSearch）

`RedisVectorConfig` 按业务域拆分，不再共用 `aa_rag_index`：

| Bean | 索引名 | 前缀 | 可过滤字段 | 用途 |
|---|---|---|---|---|
| `knowledgeVectorStore`（@Primary） | `aa_knowledge_index` | `aa_knowledge_prefix` | `knowledgeId`/`docType`/`category`/`question`/`answer` | 知识库 FAQ |
| `bookVectorStore` | `aa_book_index` | `aa_book_prefix` | `type`/`bookId`/`chunkNo`/`bookTitle`/`chapter` | 图书正文分片 |
| `memoryVectorStore` | `aa_memory_index` | `aa_memory_prefix` | `type`/`userId`/`memoryId` | 用户长期记忆 |

- 每个索引只有单一业务数据，检索用 `filterExpression` 下推到 Redis（记忆按 userId、正文按 bookId），topK 回归真实值。
- 兼容别名 `customRedisVectorStore` 指向知识库索引，避免历史注入点启动失败。
- **关键坑**：Spring AI 2.0.2 的 `RedisVectorStore.builder().build()` **不自动建索引**，必须显式 `afterPropertiesSet()`；索引已存在时 `initializeSchema=false` 跳过，重启不清数据。
- 连接参数复用 `spring.data.redis.*`（host/port/username/password/database/timeout），避免固定连 localhost 忽略生产密码。
- 旧 `aa_rag_index` 数据迁移脚本：`sql/vector_split_migrate.py`。

### 4.2 ES 图书检索（事实源在 MySQL）

`BookSearchServiceImpl` + `EsBookSearchClient`（官方 `elasticsearch-java` / rest5 客户端）：

- **一致性策略**：MySQL 是事实源，ES 只做检索。写入：图书增删改后同步索引（失败仅记日志 + 入 `pendingSync` 补偿队列）；读取：先从 ES 拿 bookId，再回 MySQL 查**实时价格/库存**。
- **降级**：ES 不可用/超时（connect 2s、request 5s）→ `searchBookIds` 返回 null → 调用方回退 MySQL FULLTEXT（ngram）+ LIKE。
- **补偿**：`@Scheduled` 定时对账（`ai.book.search.reconcile-fixed-delay`，默认 300000ms=5分钟；`initialDelay=60000`）——重试失败 bookId + 比对 MySQL/ES 集合补缺失删幽灵；分布式锁 `lock:es:book:bootstrap` 保证多实例单执行。
- 启动时索引为空则异步全量同步（`bootstrap-on-start: true`）。
- 索引名 `biz_book_search`，URI `http://127.0.0.1:9220`（9200/9300 被占用）。

### 4.3 Redis 存储与缓存（`AiChatStore` + 配置缓存）

| Key | 结构 | 内容 | TTL |
|---|---|---|---|
| `hot:question:detail` | Hash | 归一化问题 → 标准答案 | 滑动 7200s |
| `hot:question:rank` | ZSet | 归一化问题 → 热度分 | 滑动 7200s |
| `hot:question:display` | Hash | 归一化问题 → 首次提问原文 | 滑动 7200s |
| `chat:history:{contextId}` | List | 多轮问答（最新在前，最多 6 轮，单轮截断 q200/a400） | 24h |
| `ai:cache:categories` | String(JSON) | 图书分类 | 5min |
| `ai:cache:book-titles` | String(JSON) | 全部书名 | 5min |
| `ai:cache:intents` | String(JSON) | 意图列表 | 5min |

- 低频配置缓存统一走 `loadConfigCache(key, TypeReference, Supplier)`：Redis 优先 → 未命中查库回填 → Redis 故障降级查库 → DB 异常正常上抛。多实例天然一致，不再重启即丢。
- 热门池准入见 §3 步骤 8。

### 4.4 用户画像与长期记忆（`AiMemoryServiceImpl`）

- **写入**：每轮对话后 `@Async` 调大模型抽取结构化记忆（preference/fact/concern 三类），去重后写 `ai_user_memory` + `aa_memory_index`，再基于最近 8 条刷新 `ai_user_profile`（摘要 ≤900 字 + 标签 ≤8 个）。含个人信息问句返回 `[]` 时允许再抽一次。
- **读取**：`buildUserContext` = 画像摘要/标签 + 最近 5 条记忆 + 语义召回 3 条（`filterExpression("userId == '…'")` 下推 + 二次校验防串线），命中计入 `hit_count`。
- 调试：`GET /api/v1/chat/profile/{userId}` 返回画像、记忆及真实注入 Prompt 的文本。

### 4.5 图书内容 RAG（`AiBookContentServiceImpl`）

- 上传 txt/md/pdf → UTF-8 解码（PDFBox 抽文本）→ 按 500 字滑窗分片（重叠 50，尽量在句号处断）→ 落 `biz_book_chunk` → 写 `aa_book_index`（批 50）。
- 事务提交后才把 `.uploading` 临时文件改正式名；重传时清理残留向量（按 bookId 精确删）。
- 检索按书名分组取片段（避免跨书挤占），threshold=0.3。

### 4.6 异步与限流

- `AiAsyncConfig` 两个**有界**线程池：`aiTaskExecutor`（core/max 有上限，队列 200，`CallerRunsPolicy`，用于 ES 同步/索引）与 `aiMemoryExecutor`（`DiscardPolicy`，用于记忆抽取，不阻塞响应）。
- 限流 Redis fail-open：Redis 挂了不阻断问答（宁可冒一点额度风险也不让服务不可答）。

| 大模型密钥 | Nacos `ruoyi-system-ai-dev.yml` | 智谱 `glm-4-flash` + `embedding-3`(256)；**改后需重启**（ChatModel/EmbeddingModel 启动时构建，动态刷新不重建） |
| 测试开关 | `application.yml` `ai.chat.test-security-bypass: false` | 仅本地直连实例开启，生产必须 false |

## 七、关键设计决策与坑（面试高频）

1. **确定性优先**：库存/订单/发货/推荐都走结构化数据，只有开放问答才用大模型——从根上抑制幻觉。
2. **Prompt 分层 + XML 隔离**：规则在 system、数据在 user 并 XML 包裹；画像不当经营范围、不复述隐私；后置 `guardHallucinatedTitles` 二次拦截编造。
3. **向量库拆分**：三类数据独立索引 + filter 下推，解决共用索引时"片段互相挤占、跨用户记忆召回"；`build()` 后必须 `afterPropertiesSet()` 才建索引。
4. **ES 只检索不存真值**：价格/库存回 MySQL 查实时值；失败降级 FULLTEXT+LIKE + 定时对账补偿。
5. **热门池隐私准入**：只收通用标准答案，个性化/大模型回答一律不进。
6. **fail-closed 身份**：订单/画像/记录一律以登录态 userId 为准，匿名不查；测试开关仅本地开。
7. **缓存降级**：Redis/向量/ES 故障都"降级不报错"，优先保证问答可用。
8. **改动必须重启服务**：`mvn compile` 只更新 class 文件，运行中的 JVM 不热加载——"改了没生效"先查服务是否重启、class 时间戳、源码是否含返回的那串字面量。

## 八、一次典型问答的时序（开放问题示例）

```
用户："给孩子推荐几本科幻书，预算150"
 → validate + 身份绑定 + 限流 + touchProfile
 → 订单号？否 → 发货词？否 → 在售查询？否（推荐类） → 热门缓存？未命中
 → 意图识别=图书推荐（TASTE_HINTS"孩子/预算"+ BOOK_WORDS）
 → recommendBooks：解析预算→从 biz_book(ES/MySQL) 拉真实书单→过画像→Prompt 生成
 → guardHallucinatedTitles：书名/价格真实性校验
 → 落对话记录 + 异步抽取记忆（"家里有小孩""预算150"）刷新画像
 → 返回（intent=图书推荐，不进热门池）
```

> FAQ 类（如"订单多久发货"）在步骤 5 直达返回，不调用大模型；带书名问发货且本人有订单则在步骤 1.15 直接返回真实状态。
