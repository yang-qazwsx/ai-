## 智能客服问答提速（1+2+3 一起落地）

用户反馈「问题速度慢」，诊断结论：瓶颈不在本地代码，而在 `glm-4.5` 同步生成（约 13s，占总量 85%+）；
订单号直达 45ms / 热门缓存 39ms 证明本地链路都快。次要开销是外网 Embedding（~1s）。
放大器是缓存 key 用「原始问题文本」精确匹配，换个说法就 miss，导致几乎每次都重走大模型。

### 已做改动
- `application.yml`：`spring.ai.openai.chat.model` 从 `glm-4.5` 改为 `glm-4-flash`；新增
  `ai.chat.direct-similarity-threshold: 0.80` 与 `ai.chat.direct-text-match-enabled: true`。
- `AiServiceImpl.java`：
  - 新增「知识库直达」分支（向量检索后、构造 Prompt 前），命中即返回知识库标准答案，
    跳过 LLM，同时存聊天记录 + 写缓存。intent = `知识库直达`。
  - 归一化缓存 key：`normalizeQuestion()` 做全角转半角→小写→去客套/语气词→去标点→
    疑问词同义归一（怎么/怎样/咋→如何，啥时候/什么时候→多久，`查(?!询)`→`查询`）→
    兜底防削空。cacheHotAnswer() 统一写 detail/rank/display 并统一 TTL。
  - 新增 `hot:question:display`（归一化 key → 首次提问原文），`getHotQuestions` 优先用它展示，
    旧数据无 display 时退回 member，保持兼容。
  - 修正历史 bug：原缓存只判断 `relatedKnowledges` 非空，会把「召回 3 条但大模型返回兜底话术」
    的答案缓存住；现在加 `FALLBACK_MARKER = "暂时无法解答"` 判断，兜底答案不缓存。
  - 加轻量分段耗时埋点 `logCost()`（热门缓存命中 / 知识库直达 / 大模型生成 / 总耗时）。

### 关键技术判断（面试可讲）
- 用户原话要求「相似度 > 0.85 直达」，但 **embedding-3 是 256 维，中文问句与文档余弦相似度

  反而把原本 45ms 的快路径拖慢。改用「疑问词同义归一 + 知识库标准问法匹配」实现等价的
  语义收敛，零额外外网开销。

## 21:32 执行 A（只在 ruoyi-system）+ 真正根因水落石出

### ⚠️ 纠正前面两轮的错误结论
之前记的「Nacos 3.x 客户端缓存未刷新」「bootstrap context 冲突」**都不是根因**。
真正根因是 **JVM 文件编码**：`NacosConfigDataLoader.pullConfig()` 用 `String.getBytes()`
（平台默认编码）转字节，SnakeYAML 按 UTF-8 解码；Windows 中文环境默认 GBK，
配置里的中文注释导致 `MalformedInputException: Input length = 1`，
异常被包装成 `ConfigDataResourceNotFoundException` → 显示成 "does not exist"。
**项目自带的 `bin/run-modules-system.bat` 本来就有 `-Dfile.encoding=utf-8`**；
之前所有失败只因验证时一直用手工 `java -cp` 启动漏了这个参数。

## 23:46 修复「图书如何上架下架 = 未知意图」

### 根因（两层）
1. **数据**：`ai_intent` 表只有 4 条（修改密码 / 查询发货 / 申请退款 / 质量问题），
   完全没有图书类意图；`上架`/`下架`/`图书` 单独查 `selectByKeyword` 都是 0 行。
2. **算法（主因）**：`recognizeIntent` 只按空格/标点切分，中文整句变成一个 token；
   `AiIntentMapper.selectByKeyword` 的 SQL 是 `keywords LIKE '%用户词%'`（方向反了），
   短关键词字段不可能包含整句 → `intentCountMap` 为空 → 未知意图。
   即「只有用户恰好输入单个短关键词」才能命中，几乎所有完整中文问句都失效。
   注：intent 只是响应标签/聊天记录字段，不影响答案（答案走知识库直达/大模型）。

### 改动
- `AiServiceImpl.recognizeIntent()`：改用现成的 `intentMapper.selectAllIntents()`
  一次取全部意图，内存中对每个逗号分隔关键词做 `question.contains(word)` 反向匹配，
  跳过长度 <2 的词，按命中词长度加权（上限 6）取最高分意图。
  N 次 DB 查询降为 1 次；未加缓存（意图表小，且便于改动后立即生效）。
- 新建 `sql/ai_intent_book_management.sql`（幂等 `INSERT ... SELECT ... WHERE NOT EXISTS`），
  补「图书管理」意图：上架,下架,上架下架,图书上下架,图书状态,库存,图书管理,图书上架,图书下架。

## 11-16 图书内容问答 + 用户长期记忆/画像（大功能）

用户需求：图书管理上传书籍内容、AI 能问书籍内容、用户对话转长期记忆并建画像。
选型确认：文件上传+解析 / 全库语义检索 / **LLM 抽取+向量召回** / 画像先只入库。

### 交付
- **DDL** `sql/ai_book_memory_ddl.sql`（幂等）：`biz_book_content`、`biz_book_chunk`、
  `ai_user_memory`、`ai_user_profile`，并给 `ai_chat_record` 加 `session_id` + 两个索引。
- **实体** BizBookContent / BizBookChunk / AiUserMemory / AiUserProfile（项目无 Lombok，手写 POJO）。
- **Mapper** BizBookContentMapper（content+chunk）、AiUserMemoryMapper（memory+profile）+ 两个 XML。
- **IAiBookContentService**：上传→UTF-8 解码→500 字滑窗(重叠50,尽量句号断开)分片→落库→
  写向量库（文档ID `book-{bookId}-{chunkNo}`）→维护 content 元信息；`searchBookChunks` 检索。
- **IAiMemoryService**：`extractAndSaveAsync`（@Async + LLM 抽 JSON 记忆 + 去重 + 向量化 + 刷新画像）、
  `buildUserContext`（最近5条 + 语义召回3条）、`touchProfile`。
- **AiBookContentController**：`POST /api/v1/book-content/upload`、`GET /{bookId}`。

  对话后异步抽取记忆；`initKnowledgeVector` 清理时**排除 `aa_rag_prefixbook-`**，否则重建知识库会删掉书籍向量。

### 踩到并修掉的 3 个坑
1. **书籍向量写入成功但检索不到**：RedisVectorStore 检索回来只回填索引 schema 声明的 metadata
   （仅 knowledgeId/answer），自定义的 `type/bookId` 会丢。改用**文档ID前缀 `book-`** 判定，
   再回查书名补齐。存储本身是 ReJSON（不是 hash）。
2. **兜底话术被缓存**：原 `FALLBACK_MARKER` 只认「暂时无法解答」，模型说「未找到相关信息」时
   被写进热门缓存，之后一直回放错误答案。改为 `FALLBACK_MARKERS` 数组 + `isFallbackAnswer()`，
   并把「书籍命中」也计入可缓存条件。
3. **记忆抽取被书籍情节污染**：模型把「宝玉发现三十七卷古籍」当用户偏好，且输出非法 type `user|fact`。
   收紧 EXTRACT_PROMPT（明确禁止提取书籍情节/客服话术/一次性问题）+ 保存时校验 type 枚举。

### 已知限制（未处理，供后续）
- 推荐场景存在**幻觉**：知识库/书籍都没有恐龙类图书时，模型编造《恐龙大揭秘》等书名。
  正确做法是先查 `biz_book` 真实库存再让模型组织语言，或对推荐类意图走结构化检索。
- 书籍仅支持 txt/md（PDF 需引入 PDFBox），前端未跑构建验证。
- 记忆召回靠放大 topK 后内存过滤 userId，文档量大了需要把 userId 做成索引字段或独立索引。
- 验证脚本 `target/e2e_book_memory.py`，日志 `target/book_memory_final.log`。

### 后台启动 9201 的坑（重要，反复踩）
