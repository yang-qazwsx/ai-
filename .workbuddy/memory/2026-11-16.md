## 发现的 4 个缺陷（未修复，待决定）
1. **D-01 中危｜推荐类幻觉**：首次运行把知识库条目「《红楼梦》第三章《地窖藏书》」当书推荐，并编造"价格在 120 元以内"；第二次未复现（非确定性）。
   根因：推荐意图未走 `biz_book` 结构化检索 + Prompt 未禁编造。建议按 category/price/stock 查真实库存。
2. **D-02 低危｜响应 intent 被覆盖**：直达分支 `setIntent("知识库直达")` 覆盖了识别结果（日志里识别是正确的）。
   建议 `AiResponseDTO` 加 `recognizedIntent` 字段。
3. **D-03 低危｜长度校验返回 code=200**：超长问题错误文案塞进 `answer`（`参数错误：…500字符`），而 @Valid 校验返回 code=500，两类行为不一致。
4. **D-04 中危｜热门问题池隐私**：`hot:question:*` 是全局 key、未按用户隔离，会把含画像的个性化问答（"给孩子挑科普书，预算120"）展示给所有人。上线前必须处理。

## 追加：图书检索改全文索引（方案 C）
### 做了什么
- `sql/biz_book_fulltext_index.sql`：幂等新增 `ft_book_search(title,category,description) WITH PARSER ngram`
- Mapper：删掉全表 `selectBookIndex()`，改为
  - `searchBookByFulltext(keyword, limit)`：MATCH...AGAINST BOOLEAN MODE，按相关度+库存排序
  - `searchBookByLike(keyword, limit)`：兜底
  - `selectOnSaleBooks(limit)`：泛问
  - 三者都只回传 book_id/title/author/price/stock/category/status，**description 只参与匹配不回传**
- Service：`answerStockQuery` 改为关键词检索（书名/主题/泛问三种），`searchBooks()` 做「全文优先 + LIKE 兜底」

### 关键实测结论（重要，别再踩）
- MySQL 8.0.46 + ngram_token_size=2，中文检索正常：`MATCH('红楼梦')`→1、`MATCH('计算机')`→2
- **ngram 对中英混排里的英文词漏检**：同一行 "Java 编程思想"，`MATCH('Java')`=0，`MATCH('Ja')`/`('Jav')`/`('ava')` 全 0，但 `LIKE '%Java%'`=5
  → 所以 C 方案必须配 LIKE 兜底，不能只靠全文索引
- EXPLAIN 证据：全文查询 `type=fulltext, key=ft_book_search`；LIKE 兜底 `type=ALL`
- 停机词表 36 个，`java` 不在其中，漏检不是停用词导致（疑似 ngram 对纯 ASCII 短词的切分/过滤行为）

### 验证
9/9 通过（书名/书名号/英文词/品类/无结果/不存在/泛问/不误判），耗时 20~59ms
注意：用户 IDEA 里 debug 跑的 9201（pid 25440）仍是旧代码，需重启

## 追加：图书检索改 Elasticsearch（方案 C 终版）
### 架构决策
- **ES 只做检索，MySQL 做事实源**：ES 返回 bookId，价格/库存回 MySQL 取实时值（改价/扣库存不依赖 ES 同步延迟）
- **不引入 ES Java 客户端**：Spring Boot 4.0.6 管的是 elasticsearch-client 9.2.8，与服务端版本强耦合；
  改为 JDK HttpClient 直连 HTTP，零版本矩阵问题，curl 能复现同一请求
- **中文分词用 ES 内置 ngram tokenizer（min=2,max=2）**，不装 IK 插件；bigram 顺带解决 MySQL ngram 漏检英文词的问题（"Java"→ja/av/va）
- ES 跑在 **9220/9320**（9200 被 ruoyi-auth、9300 被 ruoyi-file 占用）

### 代码
- `search/EsBookSearchClient.java`：ensureIndex / indexBook / deleteBook / bulkIndex / recreateIndex / searchIds（term+match_phrase+match 加权）
- `service/IBookSearchService` + `impl/BookSearchServiceImpl`：ES 检索、单本同步、全量重建、启动异步 bootstrap（索引为空才同步）
- `controller/BookSearchController`：GET /api/v1/book-search/status、POST /reindex（均无鉴权，生产需加 @PreAuthorize）
- `BizBookServiceImpl`：insert/update/delete 后同步索引（try/catch，失败只记日志）
- `AiServiceImpl.searchBooks`：ES → 空/异常则降级 MySQL 全文+LIKE
- `application.yml`：ai.book.search.{es-enabled,es-uri,index-name,bootstrap-on-start}

### 验证（9209 实例）
- 启动自动建索引 + 全量同步 3 条；`_cat/indices` 与 `_count` 一致
- 9 条问答全过；日志 "ES 检索命中" 5 次；`有Java的书吗` 走 ES（不再靠 LIKE 兜底）
- 全量重建接口返回“共 3 条”
- **降级验证**：docker stop ES → 仍正确回答（28ms/21ms），日志“ES 检索失败，降级 MySQL”，status 接口 reachable=false；重启后自动恢复
- **未验证**：图书增删改的单本同步（CRUD 有 @PreAuthorize，本地 token 是 UUID 非 JWT，直接调 403）。用户可在后台改一本书后查 `:9220/biz_book_search/_doc/{id}` 验证

### 运维

## 追加：用户画像"看不见"问题（已修 + 加可观测接口）
### 现象

### 三个原因
1. **接口不返回画像**：只注入 Prompt，响应体里没有任何画像字段，只能看 DB/日志
2. **需要先有记忆**：抽取是异步的（实测 2s，慢时 10~30s），第一轮对话后才有画像，第二轮才注入
3. **真 bug**：`buildUserContext` 的提前返回条件是 `lines.isEmpty() && summary为空`，
   **忽略了 tags** → user 1 恰好是"有 tags、无 memory、无 summary"，注入直接返回空串

- 提前返回条件加上 `hasTags`，有标签也注入 `【画像标签】`
- 新增 `GET /api/v1/chat/profile/{userId}`（`IAiMemoryService.getProfileSnapshot`）：
  返回 profile + memories + **实际注入 Prompt 的文本（injectContext）**，让画像可观测

步骤1 快照空 → 步骤2 表达偏好（"只看科幻，喜欢刘慈欣，预算两百"）→ 2s 后记忆+摘要+标签落库 →
